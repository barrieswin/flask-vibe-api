# 個人記帳本前端串接規格書（手機端畫面開發分析）

本文件由前端開發設計師角度出發，依據 `docs/交換格式.md` 與 `docs/資料表設計.md` 進行專案分析，定義個人記帳本（`ledger-api`）手機端畫面之 RESTful API 串接規格。本文件專注於前後端通訊協定、欄位型別、驗證約束與錯誤處理人話訊息，供下一步刻劃手機畫面與狀態管理時直接參照。

> **註記**：本文件所有範例中的資料列主鍵 `id` 一律以數字展示（如 `1`），實際執行時請以伺服器端資料庫自動遞增建立回傳之實體 `id` 為準。

---

## 一、 共通規則

### 1. 頂層回應結構（固定三個鍵）
所有 API 回應主體一律為標準 JSON 物件，固定且嚴格僅包含以下三個頂層鍵：

| 鍵名 | 型別 | 說明 |
| :--- | :--- | :--- |
| `code` | `Integer` | HTTP 狀態碼，其數值與 HTTP Response Header 中的狀態碼完全相同（例如 `200`、`201`、`400`、`404`、`500`）。前端可直接由 JSON 解析，亦可讀取 HTTP Status。 |
| `message` | `String` | 固定繁體中文人話訊息，向使用者說明處理結果或錯誤原因。**絕不包含資料庫表名、約束名、SQL 語法或內部堆疊追蹤**。 |
| `data` | `Object` / `Array` / `null` | 業務資料主體。成功時為物件、陣列或計算值；失敗（4xx、5xx）時固定為 `null`。 |

**標準回應基本樣板**：
```json
{
  "code": 200,
  "message": "處理成功",
  "data": {}
}
```

### 2. 狀態碼對照規範

| 狀態碼 | 意義 | 適用情境 | `data` 內容 |
| :--- | :--- | :--- | :--- |
| **`200 OK`** | 成功 | 資料查詢成功、更新成功、作廢成功或計算完成。若清單查無資料，亦回傳 200 與空陣列 `[]`。 | 物件、陣列或彙整結果 |
| **`201 Created`** | 已建立 | 資源新增成功。 | 剛寫入之該筆實體資料列物件 |
| **`400 Bad Request`** | 請求錯誤 | 必填欄位缺漏、格式不符、數值小於或等於 0、唯一值衝突（如名稱或發票號碼重複）、外鍵參照不存在、或業務邏輯衝突（如賣出超額、已入帳交易不可作廢）。 | 固定為 `null` |
| **`404 Not Found`** | 找不到資源 | 請求 URL 路徑中的資源識別碼（ID）於資料庫中不存在。 | 固定為 `null` |
| **`500 Internal Error`**| 伺服器錯誤 | 資料庫連線異常、暫時斷線或系統未預期錯誤。 | 固定為 `null` |

### 3. 客戶端不送的欄位
下列欄位由伺服器端與資料庫內部自動產生與維護，**前端在發送新增（POST）或修改（PATCH）請求時一律不送**：
- **`id`**：代理整數主鍵（64 位元 BIGINT），由資料庫自動遞增建立，客戶端不可手動指定或嘗試修改。
- **`created_at`**：記錄建立時間戳（UTC ISO 8601），由資料庫在 INSERT 時預設填入。
- **`updated_at`**：記錄最後修改時間戳（UTC ISO 8601），由後端在更新成功時寫入當前時間。

### 4. 日期、時間與數值型別規範
- **日期（Date）**：前端請求與後端回應格式固定為 ISO 8601 日期字串 `YYYY-MM-DD`（如 `"2026-08-15"`、`"2026-11-14"`）。
- **審計時間戳（Timestamp）**：後端回應之帶時區時間字串，格式為 ISO 8601 UTC 字串（如 `"2026-08-15T04:00:00.000000+00:00"`）。前端展示時應依手機當地時區格式化。
- **金額與數值（Amount / Quantity / Price / FX Rate / Ratio / Fee / Tax）**：
  - 在 JSON 交換格式中一律表示為 JSON 數值（`Number`，如整數或浮點數，如 `70.0`、`1000.0`），非包裝字串。
  - 後端以定點數計算，前端應避免不必要的浮點運算，顯示時依幣別進行千分位格式化。
- **幣別代碼（Currency）**：ISO 4217 標準三碼大寫英文字母，如 `"TWD"`、`"USD"`、`"JPY"`。預設為 `"TWD"`。

### 5. 可空欄位（Nullable）之表現
當資料欄位允許為空且無實質內容時，API 回應中該欄位之值**固定以 JSON `null` 出現**，絕不會在 JSON 物件中省略該鍵，前端介面可安心依據屬性是否存在或值是否為 `null` 進行條件渲染。例如：`"settled_on": null`、`"note": null`、`"invoice_id": null`、`"voided_at": null`。

## 二、 錯誤句子表（Error Code & Client Messages）

後端內部攔截到資料庫約束或驗證例外時，會記錄內部代碼，但對外**嚴禁洩漏資料表名、約束名、SQLSTATE 代碼、SQL 語法或 Python 堆疊**。前端接收到的一律為純人話句子，狀態碼為 400、404 或 500，`data` 為 `null`：

| 內部 `error_code` | 觸發原因與情境 | HTTP 狀態碼 | 客戶端收到的固定人話 `message` |
| :--- | :--- | :---: | :--- |
| **`conflict.unique_name`** | 帳戶、分類或標的名稱已存在，違反唯一約束 | 400 | 名稱已存在，不可重複 |
| **`conflict.duplicate_invoice_number`** | 登錄之發票號碼在系統中已存在 | 400 | 發票號碼已存在，不可重複 |
| **`conflict.duplicate_trade_id`** | 該筆投資交易已綁定過入帳記錄 | 400 | 此交易已產生入帳記錄，不可重複入帳 |
| **`conflict.duplicate_period_key`** | 該開獎期別已存在 | 400 | 該開獎期別已存在，不可重複建立 |
| **`conflict.duplicate_prize`** | 同一開獎期別重複設定相同獎號 | 400 | 該期已存在相同的獎項與中獎號碼 |
| **`validation.amount_positive`** | 金額、股數或數值小於或等於 0 | 400 | 金額必須大於 0 |
| **`validation.fx_rate_positive`** | 折合台幣匯率小於或等於 0 | 400 | 折合台幣匯率必須大於 0 |
| **`validation.source_note_required`** | 入帳的來源與備註兩者皆未填寫 | 400 | 來源與備註不可同時為空，至少需填寫一項 |
| **`validation.merchant_note_required`** | 花費的商戶與備註兩者皆未填寫 | 400 | 商戶與備註不可同時為空，至少需填寫一項 |
| **`validation.holding_insufficient`** | 賣出股數大於目前有效庫存持股 | 400 | 賣出數量超過目前持有數量 |
| **`foreign_key.not_found`** | 指定之分類、帳戶、發票或標的 ID 不存在 | 400 | 指定之分類/帳戶不存在（或指定之關聯資源不存在） |
| **`foreign_key.restrict`** | 欲刪除或異動之資料仍被其他子記錄參照 | 400 | 資料仍被其他記錄參照，無法執行操作 |
| **`not_found.resource`** | 請求路徑中的資源 ID 不存在 | 404 | 找不到指定的資源 |
| **`database.operational_error`** | 資料庫連線失敗或逾時 | 500 | 資料庫連線失敗，請稍後再試 |
| **`upstream.twse`** | 外部證交所連線逾時、無回應或網路中斷（擴充保留） | 502 / 500 | 證交所目前沒有回應 |

> **前端串接原則**：表名（如 `accounts`）、約束名（如 `uq_accounts_name`）、SQL 指令與錯誤堆疊絕不會出現在 JSON 回應中。前端在收到非 2xx 回應時，可直接將 `response.message` 顯示於畫面的 Toast 或 Alert 提示框中。

## 三、 各端點詳細規格與最小範例

本節收錄後端已提供之全部端點。依業務模組劃分，逐一列出方法、路徑、查詢參數、請求欄位、成功 `data` 欄位與最小 JSON 範例。

---

### 1. 健康檢查（Health Check）

#### 1.1 伺服器運行檢查
- **方法**：`GET`
- **路徑**：`/api/health`
- **查詢參數**：無
- **請求欄位**：無
- **成功 `data` 欄位**：
  - `status`（`String`）：伺服器狀態（固定 `"ok"`）
  - `time`（`String`）：伺服器當前 UTC 時間戳（ISO 8601）
- **最小 JSON 範例**：
```json
{
  "code": 200,
  "message": "伺服器運作正常，測試正常可以進行其他任務。",
  "data": {
    "status": "ok",
    "time": "2026-11-14T07:38:00.000000+00:00"
  }
}
```

#### 1.2 資料庫連線檢查
- **方法**：`GET`
- **路徑**：`/api/health/db`
- **查詢參數**：無
- **請求欄位**：無
- **成功 `data` 欄位**：
  - `status`（`String`）：資料庫連線狀態（固定 `"ok"`）
- **最小 JSON 範例**：
```json
{
  "code": 200,
  "message": "資料庫連線正常",
  "data": {
    "status": "ok"
  }
}
```

### 2. 帳戶模組（Accounts）

#### 2.1 取得帳戶清單
- **方法**：`GET`
- **路徑**：`/api/accounts`
- **查詢參數**：無
- **請求欄位**：無
- **成功 `data` 欄位**：陣列，每個元素為帳戶物件（包含 `id`、`name`、`kind`、`currency`、`opening_balance`、`statement_day`、`payment_day`、`created_at`、`updated_at`）
- **最小 JSON 範例**：
```json
{
  "code": 200,
  "message": "取得帳戶清單成功",
  "data": [
    {
      "id": 1,
      "name": "現金錢包",
      "kind": "cash",
      "currency": "TWD",
      "opening_balance": 0.0,
      "statement_day": null,
      "payment_day": null,
      "created_at": "2026-08-01T08:00:00.000000+00:00",
      "updated_at": "2026-08-01T08:00:00.000000+00:00"
    }
  ]
}
```

#### 2.2 新增帳戶
- **方法**：`POST`
- **路徑**：`/api/accounts`
- **查詢參數**：無
- **請求欄位**：
  - `name`（`String`，必填）：帳戶名稱（全系統唯一）
  - `kind`（`String`，必填）：帳戶種類，限 `cash`、`bank`、`credit_card`、`broker`
  - `currency`（`String`，選填）：幣別代碼，3 碼大寫，預設 `"TWD"`
  - `opening_balance`（`Number`，選填）：開帳金額，預設 `0.0`
  - `statement_day`（`Integer`，選填）：結帳日（1 至 31），非信用卡填 `null`
  - `payment_day`（`Integer`，選填）：繳款日（1 至 31），非信用卡填 `null`
- **成功 `data` 欄位**：剛新增之帳戶物件
- **最小 JSON 範例**：
```json
{
  "code": 201,
  "message": "帳戶新增成功",
  "data": {
    "id": 1,
    "name": "現金錢包",
    "kind": "cash",
    "currency": "TWD",
    "opening_balance": 0.0,
    "statement_day": null,
    "payment_day": null,
    "created_at": "2026-08-01T08:00:00.000000+00:00",
    "updated_at": "2026-08-01T08:00:00.000000+00:00"
  }
}
```

#### 2.3 取得單一帳戶
- **方法**：`GET`
- **路徑**：`/api/accounts/<int:account_id>`
- **查詢參數**：無
- **請求欄位**：無
- **成功 `data` 欄位**：單一帳戶物件
- **最小 JSON 範例**：
```json
{
  "code": 200,
  "message": "取得帳戶成功",
  "data": {
    "id": 1,
    "name": "現金錢包",
    "kind": "cash",
    "currency": "TWD",
    "opening_balance": 0.0,
    "statement_day": null,
    "payment_day": null,
    "created_at": "2026-08-01T08:00:00.000000+00:00",
    "updated_at": "2026-08-01T08:00:00.000000+00:00"
  }
}
```

#### 2.4 修改帳戶資訊
- **方法**：`PATCH`
- **路徑**：`/api/accounts/<int:account_id>`
- **查詢參數**：無
- **請求欄位**（至少填一項，不可傳 `id`）：
  - `name`（`String`，選填）：帳戶新名稱
  - `statement_day`（`Integer` / `null`，選填）：結帳日（1 至 31，傳 `null` 清除）
  - `payment_day`（`Integer` / `null`，選填）：繳款日（1 至 31，傳 `null` 清除）
- **成功 `data` 欄位**：更新後之帳戶物件
- **最小 JSON 範例**：
```json
{
  "code": 200,
  "message": "帳戶更新成功",
  "data": {
    "id": 1,
    "name": "常用現金錢包",
    "kind": "cash",
    "currency": "TWD",
    "opening_balance": 0.0,
    "statement_day": null,
    "payment_day": null,
    "created_at": "2026-08-01T08:00:00.000000+00:00",
    "updated_at": "2026-08-15T10:00:00.000000+00:00"
  }
}
```

### 3. 帳戶餘額模組（Account Balance）

#### 3.1 取得單一帳戶即時餘額
- **方法**：`GET`
- **路徑**：`/api/accounts/<int:account_id>/balance`
- **查詢參數**：無
- **請求欄位**：無
- **成功 `data` 欄位**：
  - `account_id`（`Integer`）：帳戶 ID
  - `name`（`String`）：帳戶名稱
  - `currency`（`String`）：帳戶幣別
  - `opening_balance`（`Number`）：初始開帳金額
  - `original_currency_balance`（`Number`）：原幣別即時餘額（開帳 + 轉入 - 轉出 + 入帳 - 花費 + 交易款項）
  - `twd_balance`（`Number`）：折合新台幣總餘額（依發生匯率計算）
  - `balance`、`balance_twd`（`Number`，相容舊欄位）
- **最小 JSON 範例**：
```json
{
  "code": 200,
  "message": "取得帳戶餘額成功",
  "data": {
    "account_id": 1,
    "name": "現金錢包",
    "currency": "TWD",
    "opening_balance": 0.0,
    "balance": 230.0,
    "balance_twd": 230.0,
    "original_currency_balance": 230.0,
    "twd_balance": 230.0
  }
}
```

### 4. 帳戶移轉模組（Transfers）

#### 4.1 取得移轉清單
- **方法**：`GET`
- **路徑**：`/api/transfers`
- **查詢參數**：無
- **請求欄位**：無

```json
{
  "code": 200,
  "message": "取得移轉記錄成功",
  "data": [
    {
      "id": 1,
      "transferred_on": "2026-08-05",
      "amount": 200.0,
      "currency": "TWD",
      "fx_rate_to_twd": 1.0,
      "from_account_id": 1,
      "to_account_id": 2,
      "note": "提款轉存",
      "created_at": "2026-08-05T09:30:00.000000+00:00",
      "updated_at": "2026-08-05T09:30:00.000000+00:00"
    }
  ]
}
```

#### 4.2 新增移轉記錄
- **方法**：`POST`
- **路徑**：`/api/transfers`
- **查詢參數**：無
- **請求欄位**：
  - `transferred_on`（`String`，必填）：移轉日期，格式 `YYYY-MM-DD`
  - `amount`（`Number`，必填）：移轉金額，必須大於 0
  - `from_account_id`（`Integer`，必填）：轉出帳戶 ID（不可與轉入帳戶相同）
  - `to_account_id`（`Integer`，必填）：轉入帳戶 ID
  - `currency`（`String`，選填）：幣別，預設轉出帳戶之幣別
  - `fx_rate_to_twd`（`Number`，選填）：折合台幣匯率，必須大於 0，預設 `1.0`
  - `note`（`String` / `null`，選填）：備註說明
- **成功 `data` 欄位**：剛新增之移轉物件
- **最小 JSON 範例**：
```json
{
  "code": 201,
  "message": "移轉新增成功",
  "data": {
    "id": 1,
    "transferred_on": "2026-08-05",
    "amount": 200.0,
    "currency": "TWD",
    "fx_rate_to_twd": 1.0,
    "from_account_id": 1,
    "to_account_id": 2,
    "note": "提款轉存",
    "created_at": "2026-08-05T09:30:00.000000+00:00",
    "updated_at": "2026-08-05T09:30:00.000000+00:00"
  }
}
```

## 五、 交換格式缺漏之端點說明

依據本次專案分析，`docs/交換格式.md` 未定義且後端現況未實作下列報價相關端點，前端不私自發明路由，本期手機端畫面暫以標的持有成本（`total_cost` 與 `average_cost`）展示，不呈現即時市值：
1. **抓取台股報價端點**（如 `POST /api/quotes/fetch` 或 `POST /api/instruments/<id>/quotes`）：交換格式與後端目前皆無此端點。
2. **報價清單端點**（如 `GET /api/quotes`）：交換格式與後端目前皆無此端點。
3. **單筆最新報價端點**（如 `GET /api/instruments/<id>/quote`）：交換格式與後端目前皆無此端點。

## 六、 兩份文件的差異（交換格式 vs 資料表設計）

經全面比對 `docs/交換格式.md` 與 `docs/資料表設計.md`，兩份文件在欄位命名、結構劃分與約束條件上存在若干落差。為維持系統現況運作與防護性，以下逐條列出差異，**前端一律以《交換格式》為對外唯一標準通訊約定**：

| 項次 | 業務實體 / 欄位 | 《交換格式.md》規範 | 《資料表設計.md》規範 | 差異細節說明 |
| :---: | :--- | :--- | :--- | :--- |
| **1** | **帳戶種類欄位名與枚舉** | 欄位名為 `kind`，枚舉值包含 `cash`、`bank`、`credit_card`、`broker` | 欄位名為 `account_type`，枚舉值包含 `cash`、`bank`、`credit_card`、`brokerage` | 欄位名稱不同（`kind` vs `account_type`），券商交割戶枚舉代碼不同（`broker` vs `brokerage`）。前端送 `kind: "broker"`。 |
| **2** | **帳戶初始開帳餘額** | 欄位名為 `opening_balance` | 欄位名為 `initial_balance` | 欄位名稱命名不同。前端對接使用 `opening_balance`。 |
| **3** | **帳戶信用卡週期欄位** | 包含 `statement_day`（結帳日 1-31）、`payment_day`（繳款日 1-31）兩欄位 | 無結帳日與繳款日實體欄位 | 資料表設計無此兩欄位；交換格式有此兩欄位。 |
| **4** | **帳戶在用狀態與備註** | 未定義 `is_active` 與 `description` | 包含 `is_active`（布林值）與 `description`（字串） | 資料表設計有此兩欄位；交換格式未對外暴露這兩欄。 |
| **5** | **移轉金額與手續費** | 單一欄位 `amount`（移轉金額），無手續費欄位 | 拆分為 `out_amount`（轉出金額）、`in_amount`（轉入金額）及 `fee`（手續費） | 資料表設計支援雙幣別移轉與手續費；交換格式簡化為單一 `amount`。 |
| **6** | **移轉日期時間** | 欄位名為 `transferred_on`，格式為純日期 `YYYY-MM-DD` | 欄位名為 `transferred_at`，型態為 `TIMESTAMPTZ`（帶時間戳） | 命名不同且型態不同（純日期 vs 帶時區時間戳）。前端送 `transferred_on`。 |
| **7** | **匯率欄位命名** | 所有收支、移轉與交易表統一命名為 `fx_rate_to_twd` | 統一命名為 `exchange_rate_to_twd` | 匯率欄位簡寫不同。前端對接一律以 `fx_rate_to_twd` 傳送與接收。 |
| **8** | **入帳發生日期時間** | 欄位名為 `received_on`，格式為純日期 `YYYY-MM-DD` | 欄位名為 `received_at`，型態為 `TIMESTAMPTZ` | 命名與型態不同。前端對接使用 `received_on`。 |
| **9** | **入帳來源欄位與約束** | 包含 `source` 欄位；設有約束 `source` 與 `note` 不可同時為空 | 無 `source` 欄位；僅有 `note`（可為空） | 資料表設計無 `source` 欄位；交換格式要求至少有來源或備註。 |
| **10**| **入帳關聯投資交易外鍵** | 欄位名為 `trade_id`，型態為 `Integer` | 欄位名為 `investment_transaction_id`，型態為 `BIGINT` | 外鍵欄位名稱不同。前端對接使用 `trade_id`。 |
| **11**| **花費日期時間與商戶** | 欄位名為 `spent_on`（日期）、`settled_on`（日期）、`merchant`（商戶）；約束 `merchant` 與 `note` 不可同時為空 | 欄位名為 `occurred_at`（時間戳）、`settled_at`（時間戳）；無 `merchant` 欄位；`note` 可空 | 交換格式為純日期且包含商戶欄位；資料表設計無商戶欄位。前端使用 `spent_on` 與 `merchant`。 |
| **12**| **發票主檔號碼與金額** | 號碼欄位為 `number`；金額欄位為 `amount`（約束 `amount > 0`） | 號碼欄位為 `invoice_number`；金額欄位為 `total_amount`（約束 `>= 0`） | 欄位名稱不同，金額約束邊界不同（大於 0 vs 大於等於 0）。前端使用 `number` 與 `amount`。 |
| **13**| **發票開立時間與幣別種類**| 包含 `issued_on`（純日期）、`kind`（紙本/電子）、`currency`、`fx_rate_to_twd`、`random_code`（隨機碼） | 僅有 `issued_at`（時間戳）；無 `kind`、`currency`、`fx_rate_to_twd`、`random_code`；多出 `buyer_tax_id` | 交換格式支援多幣別與隨機碼；資料表設計為純台幣時間戳。前端對接以交換格式為主。 |
| **14**| **發票對獎狀態與中獎金額**| 狀態為 `prize_status`，枚舉：`unchecked`、`lost`、`won`、`claimed`、`void`；主表無中獎金額欄位 | 狀態為 `lottery_status`，枚舉：`pending`、`unwon`、`won`；包含 `winning_prize_amount` 欄位 | 欄位名不同且枚舉不同（交換格式多出已兌獎與作廢狀態）。前端使用 `prize_status`。 |
| **15**| **發票期別編碼** | 欄位名為 `period_key`，採雙月期初標示（如 7-8 月為 `2026-07`） | 欄位名為 `period_code`，採雙數月標示（如 7-8 月為 `2026-08`） | 期別編碼約定不同（期初月 vs 雙數月）。前端送 `2026-07`。 |
| **16**| **發票號碼唯一約束範圍** | 全系統唯一（`uq_invoices_number`） | 複合唯一（`UNIQUE (period_code, invoice_number)`，同號不同期允許） | 交換格式約束更嚴謹（跨期不可重複）。前端新增重複號碼時會收到 400。 |
| **17**| **發票品項明細欄位** | 欄位名為 `name`、`line_amount`；無 `note` 欄位 | 欄位名為 `item_name`、`subtotal`；包含 `note` 欄位 | 欄位名稱不同（`name` vs `item_name`，`line_amount` vs `subtotal`）。前端使用 `name` 與 `line_amount`。 |
| **18**| **開獎期別與規則架構** | 拆分為兩張表：`draw_periods`（期別主表）與 `draw_prizes`（獎項明細） | 單一規則表：`invoice_lottery_rules`，每一列代表單一期別之單一獎項規則 | 交換格式採主從結構（期別獨立有主鍵 ID）；資料表設計採單表平鋪結構。 |
| **19**| **開獎獎項級別與匹配規則**| 欄位為 `tier`（英文代碼如 `special`、`first`、`sixth`）與 `matching_number`；無匹配方式欄位 | 欄位為 `prize_category`（中文如特別獎、頭獎）與 `match_type`（如 `exact_8`、`suffix_3`） | 交換格式使用英文級別代號，匹配方式由業務邏輯推導。前端設定獎項時送英文 `tier`。 |
| **20**| **投資標的表名與唯一性** | 資源為 `instruments`，名稱設有唯一約束（`uq_instruments_name`） | 表名為 `investment_assets`，約束為複合唯一 `UNIQUE (symbol, market)` | 交換格式不允許不同市場存在相同名稱之標的。 |
| **21**| **投資交易欄位與種類代碼**| 欄位名為 `instrument_id`、`quantity`、`price`、`cash_amount`；再投資為 `drip`，合併為 `merge` | 欄位名為 `asset_id`、`shares`、`unit_price`、`total_cash_amount`；再投資為 `dividend_reinvestment`，合併為 `reverse_split` | 欄位名稱與交易種類枚舉值不同。前端送 `instrument_id`、`quantity`、`price` 與 `drip`/`merge`。 |
| **22**| **投資交易作廢支援** | 包含 `voided_at` 欄位，提供 `POST /api/trades/<id>/void` 軟作廢端點 | 明確標註不提供軟刪除或刪除機制（第四節第 8 點） | 交換格式支援單筆交易作廢與時序排除計算；資料表設計原則上禁止刪除。 |
